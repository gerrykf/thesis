# 数据库表关系说明文档

> 健康管理系统 - 数据库表之间的关联关系详解

---

## 📊 一、数据库表概览

本系统共包含 **13张核心数据表**，可以分为以下几类：

### 1.1 表分类

| 分类 | 表名 | 说明 |
|-----|------|------|
| **用户权限** | roles, users, menus, role_menus | 用户、角色、权限管理 |
| **健康数据** | health_records, diet_records, user_goals | 健康记录、饮食、目标 |
| **食物库** | foods, food_categories | 食物信息和分类 |
| **系统监控** | login_logs, online_users, token_blacklist, system_logs | 日志、在线用户、黑名单 |

## 🔗 二、表关系详解

### 2.1 用户权限模块

#### 关系1：roles ←→ users (一对多)

**关系描述**：一个角色可以被多个用户使用

**外键关系**：
```
users.role_id → roles.id
```

**关系说明**：
- **一个角色** 可以分配给 **多个用户**
  - 例如："普通用户"角色可以分配给100个用户
  - 例如："管理员"角色可以分配给5个用户
- **一个用户** 只能拥有 **一个角色**
  - 例如：用户"张三"的role_id=1，对应"普通用户"角色

**实际应用场景**：
```
角色表 roles:
  id=1, name='普通用户', code='user'
  id=2, name='管理员', code='admin'
  id=3, name='超级管理员', code='super_admin'

用户表 users:
  id=1, username='test01', role_id=1  → 普通用户角色
  id=2, username='admin', role_id=2   → 管理员角色
  id=3, username='sadmin', role_id=3  → 超级管理员角色
```

**删除策略**：
- 删除角色时：将用户的role_id设置为NULL (`ON DELETE SET NULL`)

---

#### 关系2：roles ←→ menus (多对多，通过role_menus)

**关系描述**：一个角色可以有多个菜单权限，一个菜单可以分配给多个角色

**外键关系**：
```
role_menus.role_id → roles.id
role_menus.menu_id → menus.id
```

**关系说明**：
- **一个角色** 可以拥有 **多个菜单权限**
  - 例如："管理员"角色可以访问10个菜单
- **一个菜单** 可以分配给 **多个角色**
  - 例如："用户管理"菜单可以分配给"管理员"和"超级管理员"

**中间表 role_menus**：
- 主键：(role_id, menu_id) 联合主键
- 作用：记录哪个角色拥有哪些菜单权限

**实际应用场景**：
```
角色表 roles:
  id=2, name='管理员'
  id=3, name='超级管理员'

菜单表 menus:
  id=1, title='用户管理'
  id=2, title='系统设置'
  id=3, title='数据统计'

角色菜单关联表 role_menus:
  role_id=2, menu_id=1  → 管理员可以访问"用户管理"
  role_id=2, menu_id=3  → 管理员可以访问"数据统计"
  role_id=3, menu_id=1  → 超级管理员可以访问"用户管理"
  role_id=3, menu_id=2  → 超级管理员可以访问"系统设置"
  role_id=3, menu_id=3  → 超级管理员可以访问"数据统计"
```

**删除策略**：
- 删除角色时：级联删除关联记录 (`ON DELETE CASCADE`)
- 删除菜单时：级联删除关联记录 (`ON DELETE CASCADE`)

---

#### 关系3：menus ←→ menus (一对多，自引用)

**关系描述**：一个菜单可以有多个子菜单（树形结构）

**外键关系**：
```
menus.parent_id → menus.id
```

**关系说明**：
- **一个父菜单** 可以有 **多个子菜单**
  - 例如："系统管理"下有"用户管理"、"角色管理"、"菜单管理"
- **parent_id = 0** 表示顶级菜单（根节点）

**实际应用场景**：
```
菜单表 menus:
  id=1, title='系统管理', parent_id=0       → 顶级菜单
  id=2, title='用户管理', parent_id=1       → "系统管理"的子菜单
  id=3, title='角色管理', parent_id=1       → "系统管理"的子菜单
  id=4, title='菜单管理', parent_id=1       → "系统管理"的子菜单
  id=5, title='数据统计', parent_id=0       → 顶级菜单

树形结构:
系统管理 (id=1)
  ├── 用户管理 (id=2)
  ├── 角色管理 (id=3)
  └── 菜单管理 (id=4)
数据统计 (id=5)
```

**删除策略**：
- 无外键约束（通过代码逻辑处理）
- 建议：删除父菜单前先删除或迁移子菜单

### 2.2 健康数据模块

#### 关系4：users ←→ health_records (一对多)

**关系描述**：一个用户可以有多条健康记录

**外键关系**：
```
health_records.user_id → users.id
```

**关系说明**：
- **一个用户** 可以创建 **多条健康记录**
  - 例如：用户"张三"每天记录一次，一个月有30条记录
- **每条健康记录** 只属于 **一个用户**
- **唯一约束**：同一用户同一天只能有一条记录 (`UNIQUE KEY unique_user_date`)

**实际应用场景**：
```
用户表 users:
  id=1, username='test01'

健康记录表 health_records:
  id=1, user_id=1, record_date='2025-01-01', weight=70.5, sleep_hours=7.5
  id=2, user_id=1, record_date='2025-01-02', weight=70.3, sleep_hours=8.0
  id=3, user_id=1, record_date='2025-01-03', weight=70.0, sleep_hours=7.0

用户"test01"有3条健康记录
```

**删除策略**：
- 删除用户时：级联删除该用户的所有健康记录 (`ON DELETE CASCADE`)

---

#### 关系5：users ←→ diet_records (一对多)

**关系描述**：一个用户可以有多条饮食记录

**外键关系**：
```
diet_records.user_id → users.id
```

**关系说明**：
- **一个用户** 可以创建 **多条饮食记录**
  - 例如：用户每天记录3-4餐，一天可能有10+条记录
- **每条饮食记录** 只属于 **一个用户**

**实际应用场景**：
```
用户表 users:
  id=1, username='test01'

饮食记录表 diet_records:
  id=1, user_id=1, food_id=100, meal_type='breakfast', record_date='2025-01-01'
  id=2, user_id=1, food_id=101, meal_type='breakfast', record_date='2025-01-01'
  id=3, user_id=1, food_id=102, meal_type='lunch', record_date='2025-01-01'
  id=4, user_id=1, food_id=103, meal_type='dinner', record_date='2025-01-01'

用户"test01"在2025-01-01这天记录了4条饮食记录（早餐2条+午餐1条+晚餐1条）
```

**删除策略**：
- 删除用户时：级联删除该用户的所有饮食记录 (`ON DELETE CASCADE`)

---

#### 关系6：users ←→ user_goals (一对多)

**关系描述**：一个用户可以有多个目标

**外键关系**：
```
user_goals.user_id → users.id
```

**关系说明**：
- **一个用户** 可以设置 **多个目标**
  - 例如：同时设置"减重5kg"、"每周运动3次"、"每日摄入<2000kcal"
- **每个目标** 只属于 **一个用户**

**实际应用场景**：
```
用户表 users:
  id=1, username='test01'

用户目标表 user_goals:
  id=1, user_id=1, goal_type='weight', target_value=65, current_value=70
  id=2, user_id=1, goal_type='exercise', target_value=150, current_value=80
  id=3, user_id=1, goal_type='calories', target_value=2000, current_value=2200

用户"test01"设置了3个目标：
  1. 体重目标：从70kg减到65kg
  2. 运动目标：每周运动150分钟（当前80分钟）
  3. 热量目标：每日摄入<2000kcal（当前2200kcal）
```

**删除策略**：
- 删除用户时：级联删除该用户的所有目标 (`ON DELETE CASCADE`)

### 2.3 食物库模块

#### 关系7：foods ←→ users (多对一，创建者)

**关系描述**：多个食物可以由一个用户创建

**外键关系**：
```
foods.created_by → users.id
foods.verified_by → users.id
```

**关系说明**：
- **一个用户** 可以创建 **多个食物**
  - 例如：管理员创建了1000个食物记录
- **每个食物** 有 **一个创建者** 和 **一个验证者**（可选）

**实际应用场景**：
```
用户表 users:
  id=2, username='admin'

食物表 foods:
  id=1, name='苹果', created_by=2, verified_by=2
  id=2, name='香蕉', created_by=2, verified_by=NULL
  id=3, name='鸡胸肉', created_by=2, verified_by=2

管理员(id=2)创建了3个食物，其中2个已验证
```

**删除策略**：
- 删除用户时：将食物的created_by和verified_by设置为NULL (`ON DELETE SET NULL`)

---

#### 关系8：foods ←→ diet_records (一对多)

**关系描述**：一个食物可以被多条饮食记录引用

**外键关系**：
```
diet_records.food_id → foods.id
```

**关系说明**：
- **一个食物** 可以被 **多条饮食记录** 引用
  - 例如："鸡蛋"可以被1000个用户的饮食记录引用
- **每条饮食记录** 只引用 **一个食物**

**实际应用场景**：
```
食物表 foods:
  id=100, name='鸡蛋', calories_per_100g=144

饮食记录表 diet_records:
  id=1, user_id=1, food_id=100, quantity=50  → 用户1吃了50g鸡蛋
  id=2, user_id=1, food_id=100, quantity=100 → 用户1又吃了100g鸡蛋
  id=3, user_id=2, food_id=100, quantity=100 → 用户2吃了100g鸡蛋

食物"鸡蛋"(id=100)被3条饮食记录引用
```

**删除策略**：
- 删除食物时：限制删除，必须先删除引用该食物的饮食记录 (`ON DELETE RESTRICT`)

---

#### 关系9：food_categories ←→ food_categories (一对多，自引用)

**关系描述**：一个食物分类可以有多个子分类（树形结构）

**外键关系**：
```
food_categories.parent_id → food_categories.id
```

**关系说明**：
- **一个父分类** 可以有 **多个子分类**
  - 例如："肉类"下有"猪肉"、"牛肉"、"鸡肉"
- **parent_id = NULL** 表示顶级分类（根节点）

**实际应用场景**：
```
食物分类表 food_categories:
  id=1, name='肉类', parent_id=NULL, level=1      → 一级分类
  id=2, name='猪肉', parent_id=1, level=2         → "肉类"的子分类
  id=3, name='牛肉', parent_id=1, level=2         → "肉类"的子分类
  id=4, name='鸡肉', parent_id=1, level=2         → "肉类"的子分类
  id=5, name='蔬菜', parent_id=NULL, level=1      → 一级分类
  id=6, name='叶菜类', parent_id=5, level=2       → "蔬菜"的子分类

树形结构:
肉类 (id=1)
  ├── 猪肉 (id=2)
  ├── 牛肉 (id=3)
  └── 鸡肉 (id=4)
蔬菜 (id=5)
  └── 叶菜类 (id=6)
```

**删除策略**：
- 删除父分类时：将子分类的parent_id设置为NULL (`ON DELETE SET NULL`)

### 2.4 系统监控模块

#### 关系10：users ←→ system_logs (一对多)

**关系描述**：一个用户可以有多条操作日志

**外键关系**：
```
system_logs.user_id → users.id
```

**关系说明**：
- **一个用户** 可以产生 **多条操作日志**
  - 例如：用户每次操作（增删改查）都会记录一条日志
- **每条日志** 只属于 **一个用户**

**实际应用场景**：
```
用户表 users:
  id=1, username='test01'

系统日志表 system_logs:
  id=1, user_id=1, action='create', resource='health_record'
  id=2, user_id=1, action='update', resource='profile'
  id=3, user_id=1, action='delete', resource='diet_record'

用户"test01"产生了3条操作日志
```

**删除策略**：
- 删除用户时：将日志的user_id设置为NULL，保留日志记录 (`ON DELETE SET NULL`)

---

#### 关系11：users ←→ login_logs (一对多)

**关系描述**：一个用户可以有多条登录日志

**外键关系**：
```
login_logs.user_id → users.id (无外键约束，通过代码关联)
```

**关系说明**：
- **一个用户** 可以产生 **多条登录日志**
  - 例如：用户每次登录（成功或失败）都会记录一条日志
- **每条登录日志** 只属于 **一个用户**

**实际应用场景**：
```
用户表 users:
  id=1, username='test01'

登录日志表 login_logs:
  id=1, user_id=1, status=1, login_time='2025-01-01 08:00:00'
  id=2, user_id=1, status=1, login_time='2025-01-02 09:00:00'
  id=3, user_id=1, status=0, login_time='2025-01-03 10:00:00', error_message='密码错误'

用户"test01"有3条登录日志（2次成功，1次失败）
```

**删除策略**：
- 无外键约束，通过代码逻辑处理

---

#### 关系12：users ←→ online_users (一对多)

**关系描述**：一个用户可以在多个设备上同时在线

**外键关系**：
```
online_users.user_id → users.id (无外键约束，通过代码关联)
```

**关系说明**：
- **一个用户** 可以有 **多条在线记录**
  - 例如：同时在手机端和PC端登录
- **每条在线记录** 只属于 **一个用户**

**实际应用场景**：
```
用户表 users:
  id=1, username='test01'

在线用户表 online_users:
  id=1, user_id=1, client_type='h5', ip='192.168.1.100', login_time='2025-01-01 08:00:00'
  id=2, user_id=1, client_type='admin', ip='192.168.1.101', login_time='2025-01-01 08:05:00'

用户"test01"同时在H5端和后台管理端在线
```

**删除策略**：
- 无外键约束，通过定时任务清理过期记录

**关系描述**：一个用户可以有多个被拉黑的Token

## 🔍 四、关键约束说明

### 4.1 外键约束策略

| 删除策略 | 使用场景 | 说明 |
|---------|---------|------|
| **CASCADE** | health_records, diet_records, user_goals, role_menus | 主表删除时，从表数据一起删除 |
| **SET NULL** | users.role_id, foods.created_by, system_logs.user_id | 主表删除时，从表外键设置为NULL |
| **RESTRICT** | diet_records.food_id | 从表有数据时，禁止删除主表数据 |

### 4.2 唯一约束

| 表名 | 唯一约束 | 说明 |
|------|---------|------|
| users | username | 用户名唯一 |
| roles | code | 角色标识唯一 |
| health_records | (user_id, record_date) | 用户每天只能有一条健康记录 |
| role_menus | (role_id, menu_id) | 联合主键，防止重复分配 |

## 💡 五、实际应用示例

### 示例1：查询用户的所有健康记录

```sql
-- 一对多关系查询
SELECT
    u.username,
    hr.record_date,
    hr.weight,
    hr.sleep_hours
FROM users u
LEFT JOIN health_records hr ON u.id = hr.user_id
WHERE u.id = 1
ORDER BY hr.record_date DESC;
```

### 示例2：查询角色的所有菜单权限

```sql
-- 多对多关系查询
SELECT
    r.name AS role_name,
    m.title AS menu_title,
    m.path
FROM roles r
INNER JOIN role_menus rm ON r.id = rm.role_id
INNER JOIN menus m ON rm.menu_id = m.id
WHERE r.id = 2;
```

### 示例3：查询菜单的树形结构

```sql
-- 自引用关系查询（查询所有顶级菜单及其子菜单）
SELECT
    parent.id AS parent_id,
    parent.title AS parent_title,
    child.id AS child_id,
    child.title AS child_title
FROM menus parent
LEFT JOIN menus child ON parent.id = child.parent_id
WHERE parent.parent_id = 0
ORDER BY parent.rank, child.rank;
```

### 示例4：查询用户的饮食记录及食物信息

```sql
-- 多表关联查询（一对多 + 一对多）
SELECT
    u.username,
    dr.record_date,
    dr.meal_type,
    f.name AS food_name,
    dr.quantity,
    dr.calories
FROM users u
INNER JOIN diet_records dr ON u.id = dr.user_id
INNER JOIN foods f ON dr.food_id = f.id
WHERE u.id = 1 AND dr.record_date = '2025-01-01'
ORDER BY dr.meal_time;
```

### 示例5：统计每个用户的目标数量

```sql
-- 一对多聚合查询
SELECT
    u.id,
    u.username,
    COUNT(ug.id) AS goal_count,
    SUM(CASE WHEN ug.status = 'active' THEN 1 ELSE 0 END) AS active_goals,
    SUM(CASE WHEN ug.status = 'completed' THEN 1 ELSE 0 END) AS completed_goals
FROM users u
LEFT JOIN user_goals ug ON u.id = ug.user_id
GROUP BY u.id, u.username;
```

## 📌 六、数据完整性保证

### 6.1 参照完整性

通过外键约束保证数据的参照完整性：

1. **不能删除被引用的数据**
   - 例如：食物被饮食记录引用时，不能删除该食物 (RESTRICT)

2. **级联删除关联数据**
   - 例如：删除用户时，自动删除其所有健康记录 (CASCADE)

3. **外键置空**
   - 例如：删除角色时，将用户的role_id设置为NULL (SET NULL)

### 6.2 实体完整性

通过主键约束保证每条记录的唯一性：

- 所有表都有自增主键 (id)
- 部分表有联合主键 (如 role_menus)

### 6.3 域完整性

通过字段约束保证数据的有效性：

- NOT NULL约束：必填字段
- ENUM约束：枚举值限制
- DEFAULT约束：默认值
- CHECK约束：数值范围限制

## 🎯 七、性能优化建议

### 7.1 索引优化

已创建的关键索引：

| 表名 | 索引类型 | 索引字段 | 作用 |
|------|---------|---------|------|
| users | 普通索引 | username, email, phone | 加速登录查询 |
| health_records | 联合索引 | (user_id, record_date) | 加速用户健康记录查询 |
| diet_records | 联合索引 | (user_id, record_date) | 加速用户饮食记录查询 |
| foods | 全文索引 | (name, name_en, description) | 加速食物搜索 |
| menus | 普通索引 | parent_id, rank | 加速菜单树查询 |

### 7.2 查询优化建议

1. **使用索引字段查询**
   ```sql
   -- 好：使用索引字段
   SELECT * FROM users WHERE username = 'test01';

   -- 差：使用非索引字段
   SELECT * FROM users WHERE nickname = '张三';
   ```

2. **避免全表扫描**
   ```sql
   -- 好：带WHERE条件
   SELECT * FROM diet_records WHERE user_id = 1 AND record_date = '2025-01-01';

   -- 差：全表扫描
   SELECT * FROM diet_records;
   ```

3. **使用LIMIT分页**
   ```sql
   -- 好：分页查询
   SELECT * FROM health_records WHERE user_id = 1 ORDER BY record_date DESC LIMIT 10;

   -- 差：查询所有数据
   SELECT * FROM health_records WHERE user_id = 1 ORDER BY record_date DESC;
   ```
